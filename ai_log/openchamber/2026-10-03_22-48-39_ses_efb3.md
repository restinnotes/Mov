## PART 2 — T4 Restructuring Design

### 2.1 Design principles

1. **Use the existing permission system; don't bypass it.** Every new host capability is a new `require_user` + course/game-scoped check endpoint (or a re-scoped existing service function). Admin keeps `require_admin`. Admins retain host/player functionality **as secondary** by keeping the ADMIN-bypass path in the same `assert_*` helpers — not by calling admin endpoints from the host UI.
2. **Game-belongs-to-course is a data-model change, not a UI move.** The current "any game × any course at room time" pairing is the root mismatch. T4 must resolve it in the schema + migration + API + checks, then reflect it in the UI.
3. **No silent privilege escalation.** The most dangerous failure is a host editing a roster/game/session for a course they don't host. Every new endpoint must re-derive scope server-side from `user_course_access` / game ownership — never trust a client-supplied `course_id` alone.
4. **Exports/reports are pure functions of `(db, session_id)`** — reuse `export_service` / `report_service` as-is from new host endpoints; add only authz wrappers.

### 2.2 The core architectural decision: games belong to a course

**Requirement:** "games attached to a specific course at creation time with course-specific Host/Player access."

**Current reality:** `games` has no course FK; `user_game_access` is global; course×game pairing is chosen per-room in `HomePage` and validated as two independent `assert_host_can_use_*` checks in `create_room`.

**Decision: add `games.course_id` (nullable during migration, non-null after) and make course-HOST the primary authorizer; retire `user_game_access` as the hosting gate (keep table read-only for migration, remove in a later release).**

```
Game { id, title, description, max_players, course_id FK → courses.id (ON DELETE CASCADE or RESTRICT — see §2.2.1), created_by, created_at }
```

Authorization after T4:

```
can_host_game(user, game) =
  user.role == ADMIN
  OR EXISTS UserCourseAccess(user, game.course_id, HOST)

can_run_session(user, course_id, game_id) =
  game.course_id == course_id            // same-course invariant
  AND can_host_game(user, game)
```

Why this wins over alternatives:

- **Alt A — keep games global, add "course-game link" join table.** Loses: preserves the two-independent-grants confusion, requires a third grant type, and every check becomes a 3-way join. More flexible (one quiz reused across courses) but T4 explicitly wants course-attached games; cross-course reuse is handled by JSON export/import (already exists) instead.
- **Alt B — keep `user_game_access` and auto-grant on game creation.** Loses: two sources of truth diverge (grant revoked but course-HOST remains, or vice versa); `my-games` and room creation can disagree. Migration never converges.
- **Alt C — derive game access purely from session host (`host_user_id`).** Loses: conflates authorship with hosting; breaks pre-session editing and co-hosting.

**Co-hosting falls out for free:** any user with HOST on the course can manage all games in that course and run any of them. No per-game grant UI needed in T4.

#### 2.2.1 Migration design (highest-risk piece)

Existing data: N games with no course, M sessions each binding `(game_id, course_id)`, K `user_game_access` rows.

```
Revision 004 (expand):
  1. ADD COLUMN games.course_id INTEGER NULL REFERENCES courses(id) ON DELETE SET NULL
     -- SET NULL (not CASCADE) during migration so a course delete can't
     -- wipe un-migrated games. Flip to CASCADE or RESTRICT in 005.
  2. ADD COLUMN games.created_by VARCHAR(36) NULL REFERENCES users(id) ON DELETE SET NULL
  3. CREATE INDEX ix_games_course ON games(course_id)
  4. Backfill (data migration, in Python, not raw SQL):
     for each game:
       sessions = distinct course_ids from game_sessions where game_id
       grants   = distinct user_ids from user_game_access where game_id
       if len(sessions) == 1: course_id = that course
       elif len(sessions) > 1: course_id = course of most-recent session;
                               CLONE game row (with questions) per other course
                               so no session's game pointer changes
       else (never run): course_id = course where a grant-holder has HOST;
                         else NULL → admin triage list
       delete user_game_access rows for migrated games AFTER backfill verified
  5. Downgrade: drop columns/index (clones remain — acceptable, document it).
Revision 005 (contract, one release later, after admin triage clears NULLs):
  ALTER games.course_id SET NOT NULL; flip ON DELETE to CASCADE (or RESTRICT —
  decide: CASCADE matches "course owns games"; RESTRICT is safer against
  accidental course delete wiping quiz banks. Recommend RESTRICT + explicit
  game-delete flow, since game delete already wipes sessions).
```

Failure modes: multi-course games are the norm in dev fixtures — the clone-per-course rule must copy `questions` with preserved `order_index` and keep `game_sessions.game_id` pointing at the original for its course. Dry-run the backfill as a `SELECT`-only report endpoint/script before running it. Gate 005 on `SELECT COUNT(*) FROM games WHERE course_id IS NULL = 0`.

`create_room` after T4 validates the **same-course invariant** (`game.course_id == request.course_id`, else 422) in addition to `assert_host_can_use_course`. The `course_id` in the request becomes redundant but keep it for one release (clients send it; server cross-checks) to avoid a flag-day on the player join path (`authorise_player` reads `session.course_id`, unchanged).

`my-games` changes shape: `GET /game/my-games?course_id=` returns games **in that course** the caller can host; the unfiltered variant is removed for non-ADMIN (ADMIN keeps it for the admin console's secondary host view). `HomePage` room creation becomes course-first: pick course → game list narrows to that course → create.

- T4: stop writing it (remove grant/revoke from `UserDetailPage`'s primary flow; keep the table + read endpoints for the migration window). `assert_host_can_use_game` is rewritten to the course-HOST check (same function name, new body — callers unchanged).

### 2.5 Alternatives considered and rejected (cross-cutting)
